# Rivelero — Scientific and Technical Architecture

> **Status:** Internal alpha / active research development  
> **Purpose:** Canonical scientific and technical reference for development, handover, validation, and future extension of Rivelero.

---

## 1. What is Rivelero?

Rivelero is a spatial framework for reconstructing and analysing **observation opportunity** generated by a survey.

Its central question is:

> **Given a particular survey, environment, spatial domain, and set of visibility assumptions, where could observation have occurred?**

This is particularly relevant to opportunistic and heterogeneous observations such as:

- street-view imagery;
- crowdsourced photographs;
- UAV and mobile surveys;
- camera networks;
- citizen-science observations;
- historical surveys;
- simulated surveys;
- prospective survey designs.

Rivelero does not assume that the existence of observations implies uniform observation opportunity.

Instead, it reconstructs the spatial observation process itself.

At the highest level, Rivelero deliberately separates four components:

```text
SURVEY
What observation opportunities existed?

ENVIRONMENT
What physical world did they operate in?

ANALYSIS DOMAIN
Where are we evaluating observability?

VISIBILITY CONFIGURATION
Under what assumptions is visibility defined?
```

These produce the central deterministic result:

```text
ViewpointConfiguration
        +
Environment
        +
AnalysisDomain
        +
VisibilityConfiguration
        │
        ▼
Individual effective visibility
        │
        ▼
Survey Observability Field
```

Formally:

```text
SOF = F(VC, E, D, V)

VC = ViewpointConfiguration
E  = Environment
D  = AnalysisDomain
V  = VisibilityConfiguration
```

A Rivelero result is therefore **not defined by the Viewpoints alone**.

Two analyses containing identical Viewpoints may legitimately produce different Survey Observability Fields because they use different:

- terrain;
- analysis domains;
- visibility distances;
- Sensors;
- directional assumptions;
- missing-metadata policies;
- or other visibility parameters.

# 2. Fundamental architectural principles

## 2.1 Source metadata are not analytical assumptions

Rivelero preserves what the source actually provides.

For example:

```text
SOURCE DATA

heading = unknown
observer height = unknown
```

must remain unknown in the imported objects.

An analysis may subsequently specify:

```text
ANALYTICAL ASSUMPTIONS

missing heading
    → treat as omnidirectional

missing observer height
    → use 1.75 m
```

but these assumptions belong to `VisibilityConfiguration`.

They must **not** be written back into the source `Viewpoint`.

This separation is fundamental for:

- provenance;
- reproducibility;
- sensitivity analysis;
- simulation;
- future uncertainty propagation;
- future Bayesian observability.

The general rule is:

```text
What the source said
        ≠
What Rivelero assumed
```

---

## 2.2 Canonical scientific objects are independent of the GUI

The GUI does not maintain alternative scientific representations.

There is no separate:

```text
GUIViewpoint
GUIEnvironment
GUIObservabilityField
```

The canonical scientific objects remain authoritative.

`ApplicationState` coordinates those objects for the desktop application, but the:

```text
core
visibility
observability
analysis
project
export
```

layers remain independent of Qt.

This allows the scientific components to be used headlessly and prevents the GUI from becoming the source of scientific truth.

---

## 2.3 Derived results must remain traceable to their inputs

A visibility result is meaningful only relative to the inputs that produced it.

Rivelero therefore fingerprints the scientific inputs that affect individual visibility.

Changing relevant:

```text
Viewpoint metadata
ObservationEvent metadata
Sensor metadata
terrain
AnalysisGrid
AnalysisDomain
VisibilityConfiguration
```

must not silently reuse an incompatible cached viewshed.

---

## 2.4 Spatial states are not interchangeable

Rivelero formally distinguishes:

```text
OUTSIDE DOMAIN
       ≠
INVALID
       ≠
BLIND SPOT
       ≠
OBSERVABLE
```

In particular:

> **NoData is not a blind spot.**

A blind spot must:

1. lie inside the `AnalysisDomain`;
2. contain sufficient valid environmental information;
3. therefore be analysable;
4. have zero reconstructed observation opportunity.

This distinction is preserved throughout:

```text
SurveyObservabilityField
GUI
analysis
GeoTIFF export
figures
provenance
reports
```

---

## 2.5 Analysis is descriptive unless an objective is explicitly defined

Repeated coverage is not automatically “waste”.

A sampling unit with no unique spatial contribution is not automatically “useless”.

Repeated observations may provide:

- robustness;
- temporal information;
- alternative viewing angles;
- better imagery;
- resilience to observation failure;
- future uncertainty reduction.

Rivelero therefore reports measurable consequences rather than imposing a universal definition of survey quality.

# Part I — Survey representation

## 3. Viewpoint

A `Viewpoint` represents a spatial observer configuration.

It answers:

> **Where and how can observation occur?**

A Viewpoint may contain:

```text
viewpoint_id

x
y
CRS
z

observer height

heading
pitch
roll

horizontal FOV
vertical FOV

sensor_id
platform

source
source_id

position uncertainty
orientation uncertainty

provenance
extra metadata
```

A Viewpoint is **not** an observation occurrence.

Coordinates also do not define identity.

For example:

```text
VP001 → (500000, 4100000)
VP002 → (500000, 4100000)
```

is valid.

The two Viewpoints may differ in:

```text
orientation
Sensor
observer height
source
time-independent acquisition configuration
provenance
```

### Current status

**Implemented.**

Position and orientation uncertainty can currently be represented but are not yet propagated probabilistically through visibility.

---

## 4. Sensor

A `Sensor` describes the sensing system.

It is separate from both Viewpoint and platform.

For example:

```text
Platform
    UAV

Sensor
    multispectral camera

Viewpoint
    position + orientation + viewing geometry
```

Sensor metadata may include:

```text
sensor ID
modality
manufacturer
model

image dimensions

focal length
physical sensor dimensions

horizontal FOV
vertical FOV

spectral information
spatial resolution

source
extra metadata
```

### Current status

**Implemented.**

Horizontal Sensor FOV can currently contribute to effective visibility-parameter resolution.

Other Sensor properties are preserved even when they are not yet used by the visibility engine.

---

## 5. ObservationEvent

An `ObservationEvent` represents an occurrence associated with a Viewpoint.

It answers:

> **When did this observation opportunity occur and where does it belong in the acquisition sequence?**

For example:

```text
A → B → C → B → D
```

can contain one Viewpoint B but two distinct ObservationEvents referring to B.

This avoids duplicating spatial identity merely because the same location was visited more than once.

Events can preserve:

```text
event_id
viewpoint_id

timestamp

sequence_id
sequence_index

image_id
source

event-specific observer height

event-specific heading
pitch
roll
FOV

acquisition conditions

provenance
extra metadata
```

### Current status

**Implemented.**

ObservationEvents can already be used as the SOF sampling unit.

A fully temporal or spatiotemporal Survey Observability Field is future work.

---

## 6. ViewpointConfiguration

A `ViewpointConfiguration` defines the complete survey strategy being evaluated.

It answers:

> **Which observation opportunities constitute this survey?**

Configurations may represent:

```text
observed
hypothetical
simulated
generated
optimized
other
```

These labels describe **provenance**, not different visibility algorithms.

A configuration can preserve:

```text
configuration ID
name
type

ordered Viewpoints
ordered ObservationEvents

description

parent configuration
derivation operation

creation time

provenance
extra metadata
```

This allows retrospective and prospective surveys to use the same scientific representation.

### Current status

**Implemented.**

Current temporary design scenarios do not yet automatically become new derived `ViewpointConfiguration` objects.

That is a deliberate future operation because committing a scenario has implications for identity and provenance.

# Part II — World and analysis context

## 7. Environment

`Environment` describes the physical world relevant to visibility.

It answers:

> **What physical spatial structure exists between observer and target?**

Conceptually:

```text
Environment
│
├── ElevationModel
│
└── EnvironmentLayers
```

The elevation model can represent:

```text
DEM
DTM
DSM
other
```

and preserves information such as:

```text
source
model type
CRS
nominal resolution
NoData
vertical metadata
provenance
extra metadata
```

Additional `EnvironmentLayer` objects can conceptually represent:

```text
buildings
vegetation
barriers
infrastructure
land cover
water
obstacles
other
```

### Current engine behaviour

The current visibility engine uses:

> **one local projected elevation raster through GDAL**

for geometric line-of-sight calculation.

Additional environmental layers are represented architecturally but are not yet integrated into the current visibility engine.

DSM is represented but has not yet been validated as a complete visibility workflow.

Environmental information affecting visibility must remain conceptually distinct from target suitability.

For example:

```text
vegetation height blocking line of sight
        ↓
Environment
```

whereas:

```text
NDVI used as habitat suitability
        ↓
downstream application / suitability model
```

The legacy potential-field/suitability implementation has been removed from the active package.

### Current status

**Partially implemented / extension-ready.**

---

## 8. AnalysisGrid

`AnalysisGrid` defines the common raster geometry.

It includes:

```text
CRS
Affine transform
width
height
X resolution
Y resolution
```

The current visibility engine requires the `AnalysisGrid` and elevation raster to match.

This common grid guarantees alignment between:

```text
AnalysisDomain
SOF
maps
analysis products
GeoTIFF exports
scenario rasters
comparison rasters
```

### Current status

**Implemented.**

---

## 9. AnalysisDomain

`AnalysisDomain` answers:

> **Where are we evaluating whether observation was possible?**

It is not merely a plotting extent.

It defines the spatial denominator used by coverage and blind-spot analyses.

Conceptually:

```text
Environment extent
┌─────────────────────────────────────────┐
│                                         │
│       AnalysisDomain                    │
│       ┌───────────────────────┐         │
│       │                       │         │
│       │     target space      │         │
│       │                       │         │
│       └───────────────────────┘         │
│                                         │
│  observer may exist outside the AOI     │
│                                         │
└─────────────────────────────────────────┘
```

Terrain outside the `AnalysisDomain` may still affect visibility.

Therefore the Environment should not automatically be cropped to the target AOI before line-of-sight calculation.

The current raster relationship is:

```text
analysable
=
analysis_mask
AND
valid_mask
```

The domain can be created from:

```text
complete terrain extent
survey extent + buffer
interactively drawn polygon
imported polygon
```

### Current status

**Implemented.**

Separate target and observer regions are represented in the architecture but are not yet general visibility-engine constraints.

# Part III — Visibility

## 10. VisibilityConfiguration

`VisibilityConfiguration` contains the assumptions under which visibility is evaluated.

It answers:

> **Under what rules should Rivelero decide whether a location is visible?**

Current configuration includes concepts such as:

```text
backend

maximum distance

default observer height
target height

horizontal directionality

default heading
default horizontal FOV

vertical-FOV fields

missing heading policy
missing FOV policy
missing observer-height policy

curvature coefficient

environment-obstacle controls

sampling unit

extra parameters
```

---

## 11. Missing metadata policies

Missing source metadata remain missing.

`VisibilityConfiguration` determines how they are interpreted for a particular analysis.

Supported policy concepts include appropriate combinations of:

```text
USE DEFAULT
OMNIDIRECTIONAL
EXCLUDE
ERROR
```

For example:

```text
Viewpoint heading = None
        │
        ▼
VisibilityConfiguration
missing heading → omnidirectional
        │
        ▼
VisibilityEngine
```

The source Viewpoint remains unchanged.

---

## 12. Visibility-parameter precedence

The general resolution hierarchy is:

```text
ObservationEvent
       │
       ▼
Viewpoint
       │
       ▼
Sensor
       │
       ▼
VisibilityConfiguration
       │
       ▼
missing-data policy
```

The exact applicable levels depend on the parameter.

For example, current resolution conceptually includes:

```text
observer height
Event → Viewpoint → Configuration

horizontal FOV
Event → Viewpoint → Sensor → Configuration

heading
Event → Viewpoint → policy/default
```

### Current status

**Implemented for the current horizontal visibility model.**

---

## 13. Current single-unit visibility engine

For one Viewpoint or ObservationEvent, the deterministic engine performs:

```text
Viewpoint / ObservationEvent / Sensor
              │
              ▼
resolve effective parameters
              │
              ▼
transform observer coordinates
              │
              ▼
GDAL terrain viewshed
              │
              ▼
restrict to analysable cells
              │
              ▼
apply horizontal heading / FOV
              │
              ▼
effective visibility mask
```

Current visibility incorporates:

```text
terrain line of sight
observer height
target height
maximum distance
Earth-curvature coefficient
horizontal direction / FOV
```

### Not currently implemented

```text
vertical FOV filtering
environmental obstacle layers
probabilistic visibility
target detectability
```

These concepts may already be represented in the architecture, but unsupported configurations must be rejected rather than treated as implemented.

# Part IV — Visibility storage and SOF construction

## 14. Why visibility is stored lazily

A real survey may contain tens of thousands of Viewpoints.

Holding every viewshed in RAM would be unnecessarily expensive.

However, simply summing viewsheds and discarding them would lose the identity of the sampling units responsible for coverage.

Rivelero therefore uses a hybrid architecture.

---

## 15. Hybrid visibility storage

```text
Viewpoint / ObservationEvent metadata
                │
                ▼
               RAM

visibility requested
                │
                ▼
      cache lookup by fingerprint
           ┌────┴────┐
           │         │
          HIT       MISS
           │         │
           ▼         ▼
         reuse    compute lazily
                     │
                     ▼
                persist to disk
                     │
                     ▼
              small LRU cache
                  in RAM
```

`VisibilityStore` therefore combines:

```text
persistent disk storage
+
small thread-safe LRU memory cache
```

A `VisibilityKey` identifies the sampling unit and relevant scientific context.

The fingerprint includes scientific inputs affecting the mask.

This prevents edited inputs with unchanged IDs from silently reusing stale visibility.

---

## 16. Important correction to the earlier SOF design

Earlier architecture discussions proposed conceptually retaining:

```text
visibility[observer, y, x]
```

inside the SOF.

The current implementation deliberately does **not** store this complete 3-D cube.

Instead:

```text
SurveyObservabilityField
│
├── aggregate exposure
├── analysis / validity state
│
└── active VisibilityKeys
          │
          ▼
    VisibilityStore
          │
          ▼
 individual visibility masks
```

This preserves the observer↔cell relationship without requiring every visibility mask to remain resident in RAM.

This is the canonical scalable implementation.

---

## 17. SurveyObservabilityField

The `SurveyObservabilityField`, or **SOF**, represents the collective deterministic observation opportunity produced by one analysis definition.

Formally:

```text
SOF = F(
    ViewpointConfiguration,
    Environment,
    AnalysisDomain,
    VisibilityConfiguration
)
```

The SOF stores or references several groups of information.

### Identity

```text
SOF ID
ViewpointConfiguration ID
Environment ID
AnalysisDomain ID
VisibilityConfiguration ID
sampling-unit type
```

### Spatial state

```text
exposure count
analysis mask
valid mask
transform
CRS
```

### Individual visibility references

```text
active VisibilityKeys
```

### Derived products

Rivelero derives:

```text
analysable mask
observable mask
blind-spot mask
categorical observability state
maximum exposure
normalized exposure
```

The categorical state is:

```text
0 = outside domain
1 = invalid
2 = blind spot
3 = observable
```

---

## 18. Exposure

For analysable cell `x`:

```text
exposure(x)
=
number of active sampling units
whose effective visibility contains x
```

Therefore:

```text
exposure = 0
    │
    ▼
blind spot

exposure = 1
    │
    ▼
unique coverage

exposure ≥ 2
    │
    ▼
repeated coverage
```

Repeated coverage is descriptive.

It does **not** mean that additional observations are scientifically unnecessary.

---

## 19. Normalized exposure

The current implemented normalization is global:

```text
normalized_exposure(x)
=
exposure(x)
/
number_of_active_sampling_units
```

This is intentionally not the only possible normalization.

A future eligibility-aware denominator could instead represent:

```text
eligible_count(x)
=
number of sampling units genuinely eligible
to sample cell x
```

and:

```text
normalized_exposure_eligible(x)
=
exposure(x)
/
eligible_count(x)
```

The scientific definition of **eligible** still requires formalization.

### Current status

**Global normalization implemented.**

**Eligibility-aware normalization designed as future work.**

---

## 20. SOF builder

The builder follows approximately:

```text
select Viewpoints or ObservationEvents
        │
        ▼
resolve Viewpoint / Event / Sensor
        │
        ▼
construct fingerprinted VisibilityKey
        │
        ▼
reuse or lazily compute visibility
        │
        ▼
add effective mask to exposure
        │
        ▼
record active key
        │
        ▼
report result
```

The build report distinguishes:

```text
requested
added
newly computed
cache hits
excluded
failed
```

Progress is exposed as:

```text
processed / total / sampling_unit_id
```

Long-running builds are executed asynchronously through the shared task infrastructure.

# Part V — Analysis and survey design

## 21. Coverage analysis

The analysis layer derives deterministic survey-level metrics from the SOF without loading every individual visibility mask.

All percentages use **analysable cells** as the denominator.

Current concepts include:

```text
observable cells
observable share

blind cells
blind share

unique coverage
repeated coverage

mean exposure
median exposure
maximum exposure

exposure distribution
```

Invalid and outside-domain cells are excluded from these scientific denominators.

---

## 22. Sampling-unit contribution

For sampling unit `i`, with visibility mask `V_i` and aggregate exposure `E`:

```text
visible_i
=
V_i within analysable space
```

```text
unique_i
=
V_i AND E == 1
```

```text
repeated_i
=
V_i AND E >= 2
```

The cells that become blind if `i` alone is removed are exactly its unique cells under the current deterministic baseline.

Individual masks are loaded lazily from `VisibilityStore`.

The complete SOF is **not** rebuilt once per unit.

An important invariant is:

```text
sum(unique cells across active units)
=
global number of cells where exposure == 1
```

---

## 23. Non-destructive design scenarios

A `SurveyDesignScenario` is a temporary modification of a baseline SOF.

It may:

```text
deactivate existing sampling units
reactivate sampling units

add temporary candidate Viewpoints

include candidates
exclude candidates

calculate scenario-relative marginal loss
calculate scenario-relative marginal gain

compare scenario coverage with baseline
```

The canonical Survey and baseline SOF are never mutated.

Scenario exposure is reconstructed from:

```text
copy(baseline exposure)
        │
        ├── subtract masks of deactivated units
        │
        └── add masks of included candidates
        ▼
scenario exposure
```

This is important because marginal effects depend on the **current scenario**, not merely on baseline contribution.

For example:

```text
cell exposure = 2
seen by A and B

remove A
→ exposure = 1
→ still observable

remove B as well
→ exposure = 0
→ blind
```

Neither A nor B necessarily had unique baseline coverage at that cell, but their joint removal creates a blind spot.

---

## 24. Candidate Viewpoints

Candidates are canonical `Viewpoint` objects.

They use the same:

```text
VisibilityConfiguration
VisibilityEngine
VisibilityKey
VisibilityStore
fingerprinting
TaskController
```

as existing survey Viewpoints.

Candidate visibility is computed lazily.

### Current limitation

Candidate additions are disabled under ObservationEvent sampling.

A coherent event-based candidate requires both:

```text
Viewpoint
+
ObservationEvent
```

and this has deliberately not yet been implemented.

Existing-unit deactivation works in both sampling modes.

---

## 25. Scenario snapshots

Temporary scenarios can be saved as lightweight snapshots.

A snapshot stores:

```text
name
description
baseline identity

deactivated unit references / keys

candidate definitions
candidate visibility keys
candidate status / inclusion

scenario summary
```

It does **not** store complete visibility-mask arrays.

Snapshots are compatible only with the baseline SOF from which they were created.

---

## 26. Scenario comparison

Compatible states can be compared using the explicit convention:

```text
RIGHT − LEFT
```

Current comparison includes:

```text
observable cells
blind cells

unique coverage
repeated coverage

coverage percentage points

mean exposure
maximum exposure

active existing units
candidate count

gained coverage
lost coverage

exposure difference
```

Swapping comparison sides reverses signed differences and exchanges gained/lost coverage.

There is deliberately **no universal Rivelero quality score**.

# Part VI — Persistence, output and reproducibility

## 27. Rivelero project files

A `.rivelero` project is a versioned ZIP-based scientific project format.

It separates:

```text
SOURCE / CANONICAL INPUTS
        │
        ▼
SCIENTIFIC ASSUMPTIONS
        │
        ▼
DERIVED RESULTS
        │
        ▼
DESIGN WORK
```

while keeping the visibility cache external and disposable.

The visibility cache is **not** the project source of truth.

Projects support:

```text
versioned schemas
atomic save
transactional load

external terrain references
terrain fingerprinting

optional persisted SOF

saved scenarios
current design state where valid

compatibility validation
```

Changed or missing terrain cannot silently validate an old SOF.

# Part VIII — Designed extensions

## 31. Physical environmental obstacles

The intended architectural rule is:

```text
obstacle data
        │
        ▼
Environment
```

while:

```text
decision to use obstacle data
        │
        ▼
VisibilityConfiguration
```

The removed legacy obstacle-density/potential-field implementation must **not** be restored as though it represented physical line-of-sight visibility.

Before implementation, Rivelero needs to formalize the relationship between:

```text
terrain surface
occluding surface
target / reference surface
```

This is particularly important for:

```text
buildings
vegetation
DSM data
```

because observer and target heights must not accidentally become relative to building roofs when they conceptually refer to terrain.

### Planned implementation sequence

```text
E1
Canonical environmental-occlusion model
        │
        ▼
E2
Obstacle ingestion / World integration
        │
        ▼
E3
Visibility-engine + cache integration
        │
        ▼
E4
Synthetic validation + export + provenance
```

**Next action:** perform a dedicated environmental-obstacle design audit before coding.

---

## 32. DSM visibility

`ElevationModelType.DSM` is represented.

A future implementation must distinguish:

```text
terrain elevation
surface elevation
observer reference elevation
target reference elevation
```

Simply substituting a DSM for a DEM may not be scientifically equivalent to modelling terrain plus above-ground obstacles.

### Status

**Represented; scientific/engine design still required.**

---

## 33. Vertical FOV

Pitch and vertical-FOV metadata/configuration are represented.

Desired behaviour:

```text
geometric line of sight
        +
vertical viewing angle
        +
pitch / vertical FOV
        │
        ▼
vertically constrained visibility
```

Angle conventions must be explicit and consistent.

### Current behaviour

Vertical FOV is not supported by the current engine.

Unsupported configurations should fail explicitly rather than silently ignoring the parameter.

---

## 34. Temporal observability

ObservationEvents already provide temporal identity and ordering.

A future temporal extension should reuse them:

```text
ObservationEvent × cell × time
```

to support:

```text
revisit frequency
temporal exposure
observation gaps
visibility persistence
trajectory analysis
```

This should extend the current architecture rather than create a separate survey model.

---

## 35. Eligibility-aware normalized exposure

Current normalization uses all active sampling units.

A future alternative may use:

```text
eligible_count(x)
=
number of sampling units that could meaningfully
have sampled cell x
```

and:

```text
normalized_exposure_eligible(x)
=
exposure(x)
/
eligible_count(x)
```

The definition of eligibility must be explicit and scientifically justified.

---

## 36. Detection and detectability

Current Rivelero estimates:

> **observation opportunity**

not guaranteed detection.

Future target-aware models may incorporate:

```text
target size
target height

projected target size

minimum visible fraction

sensor resolution
image resolution

image quality

target-specific detectability
```

These should be explicitly layered onto physical visibility rather than silently folded into the current binary visibility meaning.

---

## 37. Probabilistic / Bayesian observability

The current deterministic model evaluates:

```text
O(x) ∈ {0, 1}
```

A future uncertainty-aware model may evaluate:

```text
P(
    O(x) = 1
    |
    Survey,
    Environment,
    metadata,
    assumptions
)
```

A sensible staged development path is:

```text
heading uncertainty
        │
        ▼
probabilistic individual visibility
        │
        ▼
expected exposure
        │
        ▼
probability of blind spot
        │
        ▼
uncertainty-aware contribution
        │
        ▼
uncertainty-aware survey design
```

Later uncertainty sources can include:

```text
position
FOV
observer height
Sensor parameters
environment
```

The current architecture supports this direction because missingness and uncertainty are preserved rather than overwritten by deterministic assumptions.

---

## 38. Automated survey optimization

The current design system already provides primitives such as:

```text
marginal_gain(candidate | scenario)

marginal_loss(unit | scenario)

objective components

candidate visibility

scenario comparison
```

Future optimization should add **explicit user-defined objectives and constraints**.

For example:

```text
maximize observable area
subject to ≤ N Viewpoints
```

or:

```text
minimize number of sampling units
subject to ≥ 90% coverage
```

Later objective components may include:

```text
acquisition cost
travel distance
repeated exposure
robustness
uncertainty
```

Rivelero should not define a universal “best survey” metric.

---

## 39. Candidate pools

Future survey design may require many pre-defined candidates generated from:

```text
regular grids
roads
polygons
available imagery
simulation
adaptive strategies
```

Candidate generation should produce canonical Viewpoints or ObservationEvents and then use the normal visibility/cache architecture.

---

## 40. Simulation framework

Simulation should **not** become a separate visibility engine.

It should generate canonical Rivelero inputs:

```text
simulated Viewpoints
simulated ObservationEvents
simulated ViewpointConfiguration
synthetic Environment
VisibilityConfiguration
```

which pass through the normal pipeline.

The desired validation architecture is:

```text
known synthetic World
        +
known target field
        +
sampling strategy
        +
visibility process
        +
optional detection process
        │
        ▼
synthetic observations
        │
        ▼
Rivelero
        │
        ▼
reconstructed observability
        │
        ▼
comparison against known truth
```

This should become the experimental framework for validating future:

```text
environmental obstacles
uncertainty
Bayesian observability
optimization
sampling-bias correction
```

# Part IX — Important conceptual boundaries

## 41. Observability is not suitability

Rivelero's canonical SOF answers:

> **Could observation occur?**

A habitat/species/target suitability model answers:

> **Where is the target likely to occur?**

These may later be combined:

```text
Survey Observability
        +
Target Suitability
        │
        ▼
application-specific inference
or prioritization
```

but suitability is not intrinsic SOF state.

The legacy Rivelero potential-field/suitability packages have been removed from the active architecture.

---

## 42. Observability is not detection

`OBSERVABLE` means that the current model indicates a location could be observed from at least one sampling unit.

It does **not** necessarily mean:

```text
a target was present

a target would certainly have been detected

the image had sufficient resolution

a classifier would detect the target

a human observer would recognise the target
```

These are distinct processes.

---

## 43. SOF versus individual viewshed

```text
Individual viewshed
        │
        ▼
What can this sampling unit see?
```

versus:

```text
Survey Observability Field
        │
        ▼
What observation opportunity does the
whole survey configuration generate?
```

The SOF is a survey-level object.

Individual masks remain recoverable through its active `VisibilityKey` objects and `VisibilityStore`.

---

## 44. Baseline versus scenario

The following concepts must remain separate:

```text
baseline SOF
    ≠
temporary design scenario
    ≠
saved scenario snapshot
    ≠
future committed derived ViewpointConfiguration
```

Keeping them separate protects provenance and reproducibility.

# Part XIII — Changes from the earlier architecture

## 55. Major updates

The earlier architecture documentation remains conceptually valuable, but several elements have changed as Rivelero matured.

### 55.1 ObservationEvent sampling

**Earlier:** planned/future.

**Current:** implemented as a first-class SOF sampling mode.

---

### 55.2 Individual visibility storage

Earlier conceptual model:

```text
visibility[observer, y, x]
```

stored directly as part of the SOF.

Current scalable implementation:

```text
SOF
│
├── aggregate exposure
├── analysis / validity state
│
└── active VisibilityKeys
          │
          ▼
    VisibilityStore
```

This preserves observer-level visibility without requiring a huge in-memory 3-D cube.

---

### 55.3 Normalized exposure

**Earlier:** denominator intentionally unresolved.

**Current:** global normalization by number of active sampling units is implemented.

Eligibility-aware normalization remains future work.

---

### 55.4 Analysis package

Coverage and contribution metrics now live in the canonical:

```text
rivelero.analysis
```

package.

The old/hypothetical `metrics` architecture is no longer used.

---

### 55.5 Potential field and suitability

The old:

```text
potential field
OPF
suitability
```

implementation has been removed from the active package.

Suitability remains a conceptually valid downstream application, but it is not intrinsic SOF state.

---

### 55.6 Analysis & Design

The following are now implemented:

```text
coverage analysis

sampling-unit contribution

non-destructive scenarios

candidate Viewpoints

scenario snapshots

scenario comparison
```

---

### 55.7 Persistence and output

The following are now implemented:

```text
.rivelero project persistence

scientific raster export

scientific table export

standalone figures

provenance manifests

offline HTML reports
```

---

### 55.8 Environmental layers

Environmental layers remain represented architecturally but are not yet physically integrated into the visibility engine.

---

### 55.9 Vertical FOV

Vertical FOV remains represented but explicitly unsupported by the current engine.

---

### 55.10 Simulation and probabilistic observability

Both should extend the canonical architecture rather than create parallel engines or alternative scientific data models.

# Part XV — Handover rules

## 57. Ten rules for future development

For a new developer taking over Rivelero, the most important rules are:

### 1. Do not overwrite missing source metadata with analytical assumptions.

```text
heading = None
```

must remain source truth even if an analysis treats it as omnidirectional.

### 2. Do not treat Viewpoints, ObservationEvents, and configurations as interchangeable.

They represent different concepts.

### 3. Do not crop environmental information merely because it lies outside the target AOI.

Terrain outside the AnalysisDomain may affect line of sight.

### 4. Do not equate NoData with blind spots.

```text
INVALID ≠ BLIND
```

### 5. Do not compute and retain every visibility mask in RAM.

Use the canonical `VisibilityStore`.

### 6. Do not create parallel GUI scientific models.

The canonical models remain authoritative.

### 7. Do not treat repeated coverage as intrinsically undesirable.

It is a measurable property, not a value judgement.

### 8. Do not mutate the baseline Survey or SOF for temporary design experiments.

Use non-destructive scenarios.

### 9. Do not introduce a universal survey-quality score.

Objectives and constraints must be explicit.

### 10. Extend the canonical architecture.

Simulation, environmental obstacles, uncertainty, Bayesian observability, and optimization should extend the current canonical pipeline rather than revive the removed legacy potential-field architecture.
